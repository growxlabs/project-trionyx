# Phase 06 inspection and execution design

Phases 01–05 specifications/reports/runtime/tests were inspected in this session; original Phase 02 specification is absent. Phase 05 backend/regressions passed but live provider acceptance is still blocked. This request authorizes Phase 06 implementation without retroactively claiming earlier acceptance.

Existing dealer assignment uses dealersService.assignDistributor → repository batch and assignment ledger, then a separate audit write. Enquiry assignment/status uses contactEnquiriesService with a read, update and separate audit; canonical status schema permits NEW/IN_PROGRESS/CLOSED and does not define a narrower transition graph. Reuse that enum and reject no-ops, without inventing a transition policy. Inventory transfer validates AVAILABLE serials at one source, updates a batch and appends movement/audit. Prepared transfers use one real source, a real ACTIVE destination and at most twenty unique serials.

Add optional transaction-client parameters to these four existing services, preserving existing callers. Add a callback transaction helper for the PostgreSQL adapter and SQLite write transactions. Confirmation locks the owned preparation, source records and destination dependencies, compares exact relevant fields plus normalized updatedAt, revalidates the MD immediately before mutation, then invokes normal services. Mutation, business audit, execution telemetry and terminal workflow state commit together. Failures roll back all business changes; controlled terminal failure is recorded separately. No generic mutation tool is exposed.

One minimal trix_prepared_actions table stores an immutable typed payload and state/controlled outcome. Preparation ownership binds to authenticated MD user. Server TTL ten minutes. PREPARED→CONFIRMED→EXECUTED happens inside a single transaction; cancelled/expired/failed are terminal; repeated successful confirmation returns ALREADY_EXECUTED and cannot retry a mutation. Viewing is authenticated and performs no execution. Confirmation body contains only preparationId, explicit confirmation flag and application preview digest; stored payload supplies all targets/proposed values. UI loads the stored authoritative preview and has separate Confirm and Cancel controls. Prompt, model output, previous confirmation and navigation cannot authorize execution.

Payloads contain operational IDs/display labels/statuses/timestamps only; no customer messages/contact fields, credentials or tokens. Reason is bounded operational text and treated as data. Preparation metadata and confirmation outcome use separate sanitized TRIX logs. Business audit remains the normal domain audit. Row-level security denies direct public access to workflow storage. Retain terminal rows for at least thirty days for duplicate protection and audit linkage; no background cleanup/agent job is introduced. Pending expiry is enforced on access. Maintenance may later purge terminal rows older than thirty days, never reuse IDs, and absent purged IDs remain not found.

Only four preparation tools are advertised to the model. No confirm/cancel/execute tool exists. Application-owned same-origin MD endpoints view/confirm/cancel, with strict input size/schema and fresh auth. A minimal confirmation card is necessary for this phase; no broader TRIX UI redesign or Phase 07.

Live preparation may use real MD records, but the agent must not confirm a live business mutation on the MD's behalf. Live mutation acceptance requires the MD to click the application control after reviewing the concrete preview. Provider credit remains a separate live preparation dependency.
