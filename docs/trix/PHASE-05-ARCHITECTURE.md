# Phase 05 pre-implementation inspection

Read the Phase 01/03/04 specifications and previous implementation reports in this session. Original Phase 02 specification is absent; its report/runtime/tests are available. Phase 03/04 model acceptance was partial because of provider limits; the user explicitly requests Phase 05 work, without retroactively accepting those checks.

warrantiesService offers activation/void/policy writes and public checking plus list/detail reads. TRIX adds a minimal read repository alongside the canonical warranty repository, with the same stored fields and UTC expiry semantics. It avoids actor joins, preserves missing references for integrity checks, and never calls activation/public responses (which intentionally mask VOID) or raw detail audit payloads. warrantiesRepository joins warranty→serial/product/dealer and actor; list defaults 25, caps 100. Stored statuses ACTIVE/VOID, derived ACTIVE/EXPIRED/VOID. Installation/start/end dates are stored YYYY-MM-DD; activated_at is registration time. End date remains ACTIVE through that date using existing UTC-calendar semantics. PostgreSQL timestamps must normalize to ISO with milliseconds. serial_record_id is unique across all statuses; null dealer is a valid internal activation. Policy is product-linked with duration/status, but warranty stores dates rather than immutable policy/version FK. Policy lookup currently repairs IDs with UPDATE, so TRIX will not call it. Current inactive/missing policy cannot retrospectively prove invalid coverage.

Real WARRANTY_ACTIVATED/WARRANTY_VOIDED audit events contain warranty IDs and timestamps. Serial movements and dealer assignment ledger exist; business audit records store dealer/distributor status and enquiry lifecycle events. Normalize fixed safe event identities/timestamps and omit actors, reasons, notes, raw metadata, customer details, credentials and policy writes. Use primary ledger for inventory/assignment history and audit for other lifecycle changes, avoiding duplicate representations of the same movement/assignment.

Existing internalOverviewService delegates auth overview and includes null/unbuilt metrics; it is not a source of invented sales metrics. Reuse inventory status summary, dealer network summary/exceptions, enquiry summary/attention. Add bounded inventory-attention reads sharing existing rule SQL rather than loading unbounded exceptions. Executive results report current snapshots plus explicit activity date windows, not historical stock snapshots. Multiple repository reads are not an atomic cross-module snapshot.

Warranty→serial/product/dealer and dealer→distributor are real links. contact_enquiries has owner/product fields but no dealer_id. Requests to correlate a dealer's enquiries with warranty activity must return controlled unsupported, never fuzzy-match names/phone/email. No risk/sales/revenue/forecast metrics. Attention combines existing rule instances with per-module bounded previews and exact counts, no new urgency threshold.

Six tools only, active MD on every invocation with fresh runtime session authorization; same provider boundary, two total calls, zero retries, 30-second timeout, compact advertised tool subset and 512 output-token budget. Strict schemas/response union, maximum 50 rows/groups/events, telemetry-only forward migration. No renderer redesign, subagents, business-table migration or Phase 06.
